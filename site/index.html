libra: a multi-tenant policy evaluation engine send an entity and an input, get back allow or deny

abstract

libra decides whether a request is allowed. a service sends an entity and an input to /v1/evaluate; libra runs every policy that applies and answers ALLOW or DENY with a per-policy trace.

policies are plain javascript functions, so rules change without a redeploy. every applicable policy must allow, any deny or error denies, and every decision is recorded for audit.

status of this memo

this memo documents libra as built today. storage, the js engine, the tenant / scope / policy http api and the evaluation endpoint are in place. a kubernetes crd for policies and automatic expiry sweeping are planned in the design doc, not built.

1.introduction

authorization and business-rule checks tend to end up hard-coded across services. changing one means a redeploy, there is no audit trail of why a request was denied, and temporary rules (a promo, a freeze window) get forgotten and never removed.

libra separates the decision from its enforcement. services ask; libra decides. in particular:

  • policies are two small javascript scripts, an applicability check and the decision itself (§3.2).
  • all policies that apply to an entity are evaluated together, and the verdict is unanimous (§3.3).
  • policies are time-bound with validFrom and validTo.
  • every decision carries a trace and is recorded in policy_evaluations.

2.terminology

tenant
an organization, and the isolation boundary every call is scoped within.
scope
a group of users within a tenant, for example notification.
entity
an opaque identifier supplied by the client. libra stores no attributes for it and never interprets it; policies decide from the request's inputAttrs.
policy
a pair of javascript scripts, targeted at a whole scope (*) or at one entity, with a status and a validity window.
verdict
ALLOW or DENY, for one policy or for a whole request.

3.policy model

3.1.targeting

a request for an entity picks up both the policies written for that entity and the scope-wide * policies of the same tenant and scope.

table 1: targeting
tenantscopeentityIDapplies to
1notification*every entity in tenant 1's notification scope
1notificationaccount-holder-1only account-holder-1, in that scope

3.2.script contract

a policy holds two scripts, appliedJs and evaluatedJs. they run in separate contexts and both receive the request's inputAttrs as their only argument.

  • each script must define a top-level function named evaluate; it is the only function the engine calls.
  • evaluate must return a boolean. any other return value is an error.
  • appliedJs may be omitted, in which case the policy always applies.
  • scripts should be pure: no state kept between calls, no i/o, the same result for the same input.
// appliedJs: does this policy apply to this request?
function evaluate(input) {
    return input.channel === "sms";
}
// evaluatedJs: true allows, false denies
function evaluate(input) {
    return input.amount <= 100;
}

3.3.evaluation

given a tenant, scope, entity and inputAttrs, libra:

  1. loads every ACTIVE policy of that tenant and scope whose entityID is * or the requested entity, and whose validity window covers the current time.
  2. runs all of them in parallel on graaljs. for each, appliedJs decides whether it applies; if it does, evaluatedJs decides its verdict.
  3. treats a missing evaluate, a non-boolean result, a thrown error, or a timeout as DENY for that policy.
  4. answers ALLOW only if every applicable policy allowed, and DENY otherwise.
  5. records each policy's result in policy_evaluations under the requestID returned to the caller.

4.running libra

4.1.quickstart

start postgres and redis, build, and run the server on :8080:

docker compose up -d postgres redis
mvn clean install
java -jar libra-api/target/libra-api-1.0-SNAPSHOT.jar

then create a tenant, a scope and a policy, and evaluate a request against it:

curl -s -X POST localhost:8080/v1/tenants -H 'content-type: application/json' \
  -d '{"tenantCode": "acme", "tenantName": "Acme Corp"}'

curl -s -X POST localhost:8080/v1/scopes -H 'content-type: application/json' \
  -d '{"tenantID": 1, "scopeName": "payment"}'

curl -s -X POST localhost:8080/v1/policies -H 'content-type: application/json' -d '{
  "tenantID": 1, "scopeID": 1, "entityID": "*", "code": "max-amount",
  "evaluatedJs": "function evaluate(input) { return input.amount <= 100; }",
  "validFrom": 0
}'

curl -s -X POST localhost:8080/v1/evaluate -H 'content-type: application/json' \
  -d '{"tenantID": 1, "scopeID": 1, "entityID": "user-42", "inputAttrs": {"amount": 250}}'

the last call answers DENY, with max-amount in deniedPolicies.

4.3.schema

the schema lives in libra-core/src/main/resources/db/schema.sql. there are no migrations: docker compose applies it when the postgres volume is first created, and the app never runs it. for an existing database, apply it by hand, once; it is not idempotent:

psql -h localhost -U postgres -d libra -f libra-core/src/main/resources/db/schema.sql

5.4.evaluate

POST /v1/evaluate takes {tenantID, scopeID, entityID, inputAttrs} and answers 200 with the verdict, decided as in §3.3.

// request
{
  "tenantID": 1,
  "scopeID": 1,
  "entityID": "account-holder-1",
  "inputAttrs": { "channel": "sms", "hour": 23 }
}

// response
{
  "requestID": "…",
  "tenantID": 1,
  "scopeID": 1,
  "entityID": "account-holder-1",
  "result": "DENY",
  "deniedPolicies": ["quiet-hours"],
  "evaluations": [
    { "policyID": 7, "policyCode": "quiet-hours", "entityID": "*",
      "result": "DENY", "errors": null }
  ]
}

deniedPolicies lists the codes of policies that denied or errored. evaluations is the per-policy trace; a failed script's details are in its errors.

5.5.health

GET /healthz aggregates db (postgres), redis, disk space and ping. it answers 200 when every component is UP and 503 when any is DOWN. only component names and statuses are shown, never hosts or versions.

7.security considerations

libra has no authentication or authorization layer of its own: callers are trusted services, and it must not be exposed to untrusted clients.

policy scripts run in graaljs contexts with host access disabled: no java classes, files, network or threads. each run is bounded by a statement limit of one million and a 500 ms watchdog; a script that exceeds either is stopped, and its policy counts as DENY.

because any error denies, a broken policy fails closed. policy authors should test a script against representative inputAttrs before setting it ACTIVE.

8.testing

docker must be running: the dao tests start postgres with testcontainers.

mvn test
